# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Windows: the virtualenv interpreter is `.venv/Scripts/python.exe`. Use it rather than a bare
`python`, which resolves to a system interpreter without the dependencies installed.

```bash
.venv/Scripts/python.exe -m pytest                          # full suite; slow, run a file while iterating
.venv/Scripts/python.exe -m pytest tests/test_negotiation.py -q
.venv/Scripts/python.exe -m pytest tests/test_negotiation.py::test_name -q
.venv/Scripts/python.exe -m uvicorn dispatch_agent.webapp.main:app --reload   # FastAPI on :8000
cd frontend && npm run dev                                  # Next.js console on :3000
cd frontend && npx tsc --noEmit                             # typecheck (no test script exists)
```

Setup, if the venv is missing: `pip install -r requirements.txt && pip install -e .`, then
`python scripts/seed_db.py`.

Data scripts (the destructive ones are explicit about it):

```bash
python scripts/seed_test_clients.py    # WIPES the DB, seeds 20 synthetic clients over 5 dates
python scripts/reset_demo.py --yes     # destroys and rebuilds the DB from a known-good state
python scripts/run_demo.py             # end-to-end demo beat; needs real LLM credentials
python scripts/smoke_live_model.py     # deliberate live-provider check; not part of the suite
```

There is no linter or formatter configured. `frontend/AGENTS.md` is generated by `next dev` —
commit it with your work rather than reverting it.

## Testing constraints

`tests/conftest.py` has four autouse fixtures that make the suite *provably* offline rather than
accidentally so: a per-test SQLite file, `routing_provider=haversine` with credentials blanked,
`llm_provider=none`, and `requests.get/post` monkeypatched to raise. A test that grows a real
network call fails loudly. Tests that want the model path inject `FakeLLM` into `MessageReader`
explicitly — never by re-enabling a provider.

Because of this, every natural-language behaviour the product claims is pinned against
`planning/language.py`, the deterministic parser, not against a model.

`tests/test_browser_regressions.py` holds failures found in real browser sessions, written at the
API level on purpose — a unit test on a guard would pass with the guard wired to nothing.

## Architecture

### The one rule everything else follows

**The model chooses; deterministic code decides what is true.** Claude reads a customer message
and picks an action; it never computes a date, a drive time, a feasibility, or a window. Break
this and the guarantees below stop being guarantees.

Concretely: `agents/understanding.py` asks the model for an intent plus the *phrases* that say
when — "Saturday morning" comes back as those two words — and `planning/language.py` resolves
them against the planning clock. There is no field through which a model-computed date can enter
the system.

### Layers

- `dispatch_agent/planning/` — the deterministic core. Solve, score, negotiate, promise, record.
- `dispatch_agent/agents/scheduling_agent.py` — a bounded LangGraph loop
  (`observe → decide → act → … → finish`), capped at `MAX_TOOL_STEPS = 10`. Its own `step_count`
  is the real guard; LangGraph's `recursion_limit` is a backstop that must never be the normal
  path (it aborts the graph and discards the run log).
- `dispatch_agent/planning/tools.py` (plus `negotiation_tools.py`, imported at its bottom) — the
  `TOOL_REGISTRY` allow-list. An unregistered action returns a failed `ToolResult`, never an
  exception and never a guess. Arguments are validated against a Pydantic model with
  `extra="forbid"` before the tool runs.
- `dispatch_agent/solver.py` — OR-Tools single-vehicle TSP with time windows. A time-limited
  guided local search: good, not provably optimal. Don't describe it as optimal.
- `dispatch_agent/webapp/main.py` — FastAPI, plus `chat_api.py` mounted as a router and the
  legacy static pages at `/` and `/admin`.
- `frontend/` — Next.js 16 console (Orders `/`, Daily Routes `/routes`, Customer Chat `/chat`).
  It proxies `/api/*` to FastAPI via `next.config.ts` rewrites, so there is no CORS middleware
  and no environment-specific base URL in the client. Both processes must be running.

### Sequencing vs. negotiation — two optimisations, kept apart

Sequencing decides the **order** of a day's stops (`solver.py`, `tests/test_route_sequencing.py`).
Negotiation decides **which day and window** a customer is promised
(`planning/candidate_service.py`, `offer_service.py`, `tests/test_negotiation.py`). Keep them
separate; the model chooses between deterministic results from both.

### Four states that are load-bearing

| | what it is | where |
|---|---|---|
| stated availability | what the customer said — only they can create it | `AvailabilityOption.window` |
| service window | their solved arrival→departure | `CandidateSlotEvaluation.service_window` |
| promise window | the narrow window put to them, locked on acceptance | `OfferedSlot.window` |
| locked appointment | one they accepted; a replan may never move it | `JobRecord.locked_window` |

`record_availability` takes no windows argument — they arrive on the tool context from the
parser. There is deliberately no path from `suggest_route_aware_windows` (things *we* propose)
into `record_availability` (things the *customer* said). That is what makes "never claim the
customer is available at a time they did not give" a property of the code.

The promise window is derived from the arrival OR-Tools actually chose
(`planning/promise_window.py`), never from the availability, and is `max(120, duration + 30)`
minutes wide. Never the service interval itself: `solver._normalised_windows` reduces a lock
`[S,E]` for a `D`-minute job to an arrival domain of `[S, E-D]`, so at width `D` the arrival is
pinned and one leg re-estimating by a minute makes the whole day infeasible for everyone on it.

### Structural guards (prompts were not enough)

A live smoke test proved prose instructions fail, so these are enforced in code:

- `lock_appointment` refuses unless the customer actually accepted that slot (gpt-4o-mini called
  it while its own question was still unanswered, and succeeded).
- `send_message` sends the wording the previous tool produced (the same model rewrote an offer
  into "Dear Mrs. Lee… Best regards" and dropped the route reason the message existed to carry).
- `plan_service.assert_locks_respected` checks the solved output *before* anything is persisted.
  Trusting the solver's own infeasibility report is necessary but not sufficient — a regression
  could produce a plausible-looking plan that quietly moves a confirmed appointment.
- `offer_service.create_offer` counts persisted offer rows for the two-round cap, and acceptance
  is idempotent via a conditional UPDATE whose row count decides whether work happens.
- `chat_api.py` guarantees exactly one agent run per message; earlier duplicate offers came from
  a client making two calls.

### Other invariants worth knowing before editing

- **Never call `date.today()`.** `planning/clock.py` is the one place "today" and the bookable
  horizon are decided, so a recorded demo and the tests behave identically every run
  (`DEMO_BASE_DATE` pins it).
- **Baselines are always re-solved, never read from a stored plan** (`candidate_service.py`).
  Comparing a stored plan against a freshly solved one makes the incremental cost meaningless.
  Stored plans are for display.
- **`total_score` is a ranking index, not a quantity anyone drives.** It mixes real driving
  minutes with artificial penalties (a 60-minute empty-day charge), so it must not appear on any
  customer- or coordinator-facing surface — show the decomposition instead, each term in its own
  unit (`planning/scoring.py`, `RouteImpact.tsx`).
- **Route explanations come from `planning/route_facts.py`,** read off the solved `DaySequence` —
  never from a model, which will cheerfully name a neighbourhood the van is not going to.
- **Counteroffering is policy, not judgement** (`planning/negotiation.py`): a requested time we
  can serve is served, except when infeasible, overtime, opening an otherwise-empty delivery day,
  or another day saves `COUNTEROFFER_SAVING_MINUTES` (15) or more.
- **Plans are versioned, not overwritten** (`plan_service.py`). `day_sequences` is a cache of
  whichever version is active and is written *only* from there; two writers would let the cache
  and the history disagree.
- **`decision_record.py` contains no chain-of-thought and cannot** — it is derived entirely from
  persisted typed tool results.

### Configuration

`config.py` loads `.env.local` first (real credentials, gitignored), then `.env`. Two independent
provider choices: `LLM_PROVIDER` (`bedrock` | `openai` | `none`) and `ROUTING_PROVIDER`
(`google` | `onemap` | `haversine`). Every routing path falls back to haversine on failure, which
is what keeps the suite and the demo runnable offline. `settings` is a mutable dataclass because
tests monkeypatch individual fields.

`geo/postal_codes.py`, `geo/zones.py` and `geo/routing_client.py` are placeholders for sources the
PRD calls "reused from Stow", which this repo does not have. Each ships a working but coarse
fallback and says so in a comment.

See `README.md` for provider setup (Google needs three separate APIs enabled on one key) and
`PRD.md` for the original brief.
